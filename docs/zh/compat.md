# 版本兼容与运行环境

本页汇总 SDK 1.8 与旧版的差异、服务端兼容矩阵、编译环境、线程模型与资源上限。旧版源码不在仓库中，涉及旧版内部行为的描述以 README、CHANGELOG 和现有源码为准；无法确认的地方按“以源码为准”处理。

## 版本矩阵

| SDK 版本 | 服务端要求 | 加密方式 | 签名方式 | 说明 |
| --- | --- | --- | --- | --- |
| 1.8 | 2026-11 及以后 | 0–8 | 0–14 | 当前版本，新增 6/7/8 与 14 |
| 1.7 | 2026-09 及以后 | 0–5 | 0–13 | 接口不变，可继续使用 |
| 1.2–1.6 | 对应旧服务端 | 以服务端配置为准 | 以服务端配置为准 | 兼容，建议升级到 1.8 |

README 只给出 1.7 的算法范围（0–5 / 0–13），未逐版列出 1.2–1.6 的算法编号；旧版能力以对应服务端配置和旧版源码为准。服务端升级不会强制旧客户端升级；但使用加密 6/7/8 或签名 14 必须搭配 1.8 及以上客户端，并且服务端已开放对应算法。1.8 的接口、参数与返回结构保持不变，升级主要是重新编译与回归测试。

## 1.8 与 1.2–1.7 的差异

- 新增加密 6（AES-256-GCM）、7（ChaCha20-Poly1305）、8（XChaCha20-Poly1305），新增签名 14（带密钥 BLAKE2b-256）。
- 新增 `AES256GCM.cpp`、`ChaCha20Poly1305.cpp`、`BLAKE2b` 实现与 `tests/crypto_vectors.cpp` 固定向量测试。
- 新增 `JiYan_Key32` 密钥口径，仅用于加密 6/7/8：严格 Base64 解码后不少于 16 字节则取解码值，否则取原文，再补零或截断到 32 字节。
- 算法编号上限从 5/13 扩展到 8/14；越界配置直接报 `加密或签名方式编号非法`。
- 协议层加强了响应校验：重复 JSON 键、`rc` 回显、云控身份绑定都会导致 1003。
- 加密 5–8 与签名 13–14 是服务端会员能力，客户端不做权限判断。

心跳行为存在文档与源码不一致：README 与 CHANGELOG 描述为 10 秒级，`SDK_Heartbeat.cpp` 实际按 `std::chrono::minutes(interval)` 等待，成功后又可能用 `heartbeat_interval`（分钟）覆盖。升级时以实际源码和联调结果为准，不要仅按 README 推断。

## 服务端兼容

服务端按账号配置的加密/签名方式解密与验签，因此客户端配置必须与服务端完全一致。混合部署时，旧客户端不要配置 6/7/8 或 14，否则会得到 1002/1003 或业务错误。服务端升级后，旧算法仍然可用；新算法只对已升级且已开通会员的账号生效。

`api_url` 必须指向接口目录。`set_api_url` 会补 `http://`、补末尾 `/`，只有当地址没有路径时才补 `/api`；自定义路径不会自动改成 `/api/`。HTTPS 不被支持，HTTP 层会明确拒绝，不会静默降级。

## 编译与运行环境

| 项目 | 要求 |
| --- | --- |
| 语言标准 | C++17 |
| Android | NDK 工具链 + JNI 头文件（`jni.h`），`SDK_Init.cpp` 直接包含 |
| Linux 桌面 | g++ 或 clang++，需 POSIX socket、`dladdr`、`/proc/self/maps` |
| 构建系统 | CMake 3.16+，`find_package(JNI REQUIRED)` |
| 第三方依赖 | 无 OpenSSL、libsodium、libcurl；内置 nlohmann/json |
| 网络 | 纯 Socket HTTP/1.1，仅 `http://`，不支持 TLS |

```bash
g++ -std=c++17 -O2 -c include/jiyan/SDK_Main.cpp -Iinclude/jiyan \
    -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux"
```

源码使用 POSIX socket、`dladdr` 与 `/proc/self/maps`，并依赖 JNI 头；Windows 原生构建不在当前支持范围，如需移植要自行替换这些平台相关部分。NDK 版本与 Android API 级别未在仓库中固定，需支持 C++17 与 JNI，具体以实际编译结果为准。

## 线程模型

| 执行体 | 启动方式 | 行为 |
| --- | --- | --- |
| 请求线程 | 默认每次异步请求 detach 一个线程 | 受递归 `RequestMutex` 串行化；`is_requesting` 防止重入 |
| 心跳线程 | 卡密验证成功后启动 | 全局单线程，按间隔请求；连续失败 2 次置锁并退出 |
| 云控工作线程 | 首次 `更新()` 且有绑定时启动 | 按 `poll_after` 轮询，失败约 5 秒重试 |
| 回调 | 在请求线程或调用 `更新()` 的线程执行 | 不保证主线程，UI 操作需自行切回 |

`Enable_SingleThreaded()` 会让请求同步执行，适合控制台或不便管理异步生命周期的场景。异步接口通过引用回填 `bool&`/`std::string&`，这些变量必须比请求活得久；请求未完成时再次发起会被拒绝或直接返回。`Stop_Heartbeat()` 会 join 心跳线程；云控退出需调用 `RemoteConfig::GetInstance().Shutdown()`，它没有中文包装。

```cpp
JiYanSDK::Enable_SingleThreaded();       // 控制台或简单宿主
JiYanSDK::set_device_id("YOUR-DEVICE-ID");
// ... init 与卡密验证 ...
if (JiYanSDK::is_locked()) {
    // 连续两次心跳失败后置锁，需要重新验证卡密
}
```

## 资源与上限

- 响应正文上限 8 MiB，请求正文上限 8 MiB，响应头/分块行/尾部合计 32 KiB。
- 连接超时 15 秒，发送与接收共用 30 秒总截止时间。
- 云控最多 100 个绑定、100 条待确认 ACK、4096 个已见指令 ID；轮询间隔 1–30 秒。
- 心跳间隔被限制在 1–1440（源码按分钟使用）。
- 体积主要由内置 json.hpp 与各哈希/AEAD 实现决定，随编译选项与链接裁剪变化，以实际产物为准。

## 升级建议

1. 先升级服务端，再升级客户端；确认账号已开通所需算法。
2. 保持 1.8 的接口调用不变，重新编译并跑 `tests/crypto_vectors.cpp`。
3. 逐项核对 `Crypto_Method`、`Signature_Method`、`Crypto_Key`、`Signature_Key` 与服务端配置。
4. 回归卡密验证、解绑、心跳、云控、云更新五条链路，重点检查 1002/1003。
5. 保留旧版本回滚包；新旧客户端并存时，不要给旧客户端下发 6/7/8 或 14。

已知限制：SDK 不实现下载器、不提供 UI、不包含服务端实现；云控 `Shutdown` 无中文包装；会员能力只在服务端校验。遇到与本文不符的行为，以仓库源码为准。
